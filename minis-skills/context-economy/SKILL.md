# 上下文经济（省 token 纪律）

**核心认知**：token 消耗的大头**不是单次读取的体积，而是 (a) 重复抓取 和 (b) 把原始数据当"内容"读进来，
而不是当"输入"交给脚本处理。**

## 实测数据（2026-10-12，本机）

对同一份 GitHub README（94,434 字符）：

| 做法 | token | 说明 |
|---|---:|---|
| 天真：全文一次读完 | **23,608** | get_text 不限流 |
| 今天实际：浏览器截断 ×4 次 | **10,000** | 被迫节省，仍浪费 |
| ✅ 脚本落盘 + rg 精准提取 | **3,845** | 只取需要的 146 行 |

**纯网页场景省 62–84%。** 但更极端的在数据统计场景：

| 场景 | 原始 | 进上下文 | 节省 |
|---|---:|---:|---:|
| 应用使用记录（19,084 条） | 4.3 MB | 几百字符的结论表 | **99%+** |
| README 精准提取 | 94 KB | 15 KB | 84% |
| 网页读取（本可避免的重复） | — | — | 100% |

**判断：一条 `dumpsys` / 日志 / CSV 直接 `cat` 进对话，通常是 10⁵–10⁶ token 量级，必然爆窗口。**

## 三条纪律

### 纪律 1：大文件先落盘，用 rg 查，不要全量读

**触发线：预计内容 > 5,000 字符时，一律先落盘。**

```
# ❌ 错：直接读
browser_use get_text  → 全量进上下文

# ✅ 对：落盘 + 定位
curl -s <url> -o /tmp/doc.md
rg -n '^## |^### ' /tmp/doc.md        # 先看结构
rg -n -A15 '^## Tools' /tmp/doc.md    # 再取需要的章节
```

**要点**：
- 先 `rg '^## '` 列章节，**再决定读哪几段**。不要先读了再挑。
- `-A N -B N` 控制上下文行数，别贪。
- PDF/HTML 先转 markdown 再处理，别让浏览器渲染结果进上下文。

### 纪律 2：能脚本算的，绝不读进上下文

**心法：不要把模型当数据处理器，要当代码生成器。**

```
# ❌ 错：把 500 行日志读进来"看看"
file_read /var/log/big.log

# ✅ 对：让脚本算，只打结论
rg -c 'ERROR' /var/log/big.log
rg 'ERROR' /var/log/big.log | sed 's/.*\(error_code=[0-9]*\).*/\1/' | sort | uniq -c | sort -rn | head
```

**典型适用场景**：
- 统计 / 计数 / 去重 / 分组
- 从结构化输出里抽字段（dumpsys、JSON、CSV、SQL）
- 跨多个文件的聚合分析
- 任何"我需要知道 X 有多少 / 有哪些 / 最大的是谁"

**实测案例**：解析 `dumpsys usagestats` 的 4.3 MB / 19,084 条记录 —— 用 Python 脚本解析后
只输出一张 190 行的结论表。若直接读入，约 100 万+ token。

### 纪律 3：读过的存本地，别重复抓

**这是今天最大的实际浪费来源。**

同一 session 内对同一来源的多次抓取，**第二次开始全是纯浪费**。

```
# 第一次：抓下来存好
curl -s <url> -o /var/minis/workspace/cache/<name>.md

# 后续：全部走本地
rg '关键词' /var/minis/workspace/cache/<name>.md
```

**自查信号**（出现任一条就该停下来）：
- 我这是第二次读同一个 URL / 文件了吗？
- 我上次读到的内容，能不能从本地或记忆里拿到？
- 我是不是在用浏览器"翻页"看一份本可以一次抓下来的文档？

**建议的缓存位置**：`/var/minis/workspace/cache/`（按域名或主题命名）。同一 session 内有效。

## 决策树

```
要获取信息
├─ 是网页/文件？
│  ├─ 已抓过？ ──是──→ 从本地重启（纪律 3）
│  └─ 否 ↓
├─ 预计 > 5,000 字符？
│  ├─ 是 → 落盘 → rg 定位 → 只读需要的段（纪律 1）
│  └─ 否 → 直接读
└─ 需要的是"统计/聚合"结果？
   ├─ 是 → 写脚本，只输出结论（纪律 2）★ 收益最大
   └─ 否 → 按上面的体积判断
```

**优先级**：纪律 2（脚本化）> 纪律 3（缓存）> 纪律 1（精准提取）。
其中**纪律 2 收益最大**，因为它把 10⁵ 量级的输入压成 10² 量级的输出。

## 反面模式（别做）

| 反模式 | 问题 |
|---|---|
| `cat` 一个大文件"看看里面有什么" | 应该先 `wc -l` + `head` 探路 |
| 循环里每次调用一次工具读一条 | 应该批量读一次，脚本拆 |
| 用浏览器翻页读长文档 | 应该 curl 落盘再 rg |
| "先全读进来，我再从中挑" | 应该先看结构再读 |
| 同一个 URL 第二次走浏览器 | 应该缓存 |
| 把 JSON/CSV 原样读进来再"分析" | 应该 `jq` / 脚本处理后只取字段 |

## 边界（这些情况不必强求）

- **短内容**（< 5,000 字符）：直接读更快，别为了"纪律"绕一圈。
- **需要逐字看的正文**（如要精确引用、翻译）：必须读全文，无法避免。
- **一次性、不可预知的交互**：网页表单、验证码、需要看渲染结果的场景 —— 该用浏览器就用。
- **交互本身是目的**（用户要你"打开看看"）：按用户意图走。

**纪律的目的是省 token，不是省工具调用。** 如果为省 token 把一个工具调用拆成五个，
或者为了"精准"而漏掉关键信息导致返工，那就本末倒置了。

---

## 一句话总结

> **原始数据是输入，不是内容。让它进脚本，别让它进上下文。**
